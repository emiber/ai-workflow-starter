# review-pr

Review the target open PR (its number — provided as the argument, or stated by the user) against its linked issue(s) and the Definition of Done, following the contract in `workflow/pr-review.md`. This is the canonical playbook: Codex runs it directly and the Claude Code `/review-pr` command delegates to it. This is **read-only**: never commit, push, or modify files.

1. Read `workflow/rules.md`, `workflow/principles.md`, `workflow/pr-review.md`, `workflow/git-flow.md` (for the Definition of Done), and `workflow/issue-tracker.md`.
2. Run the preflight from `workflow/pr-review.md`. It's read-only — if one fails, stop and report the fix. It confirms `gh` is authenticated and the PR exists and is open (if merged/closed, stop — there's nothing to review).
3. Fetch the PR and pin its **snapshot** (`workflow/pr-review.md` step 1): one explicit `gh api --method GET` read on the PR's own host, giving the base and head repositories and branches and the full base and head SHAs. Find and fetch its linked issue(s). Read the diff and every file from that snapshot, with the explicit-GET requests in step 3 of the guide, never from the local checkout or `gh pr diff`. The diff runs three-dot from the merge base of the base and head SHAs. Changed and helper files come from the head repository at the head SHA (the fork, for a fork PR), old context from the base repository at the merge base, each path chosen by its status (added, modified, renamed, removed). A read that fails or comes back incomplete (no access, a 404, a missing revision, the 300-file inventory cap, a count that doesn't match) stops the review as incomplete, naming the repository, SHA and path; binary files, symlinks and submodules are named as limitations; never fall back to local files. On GitHub, carry each issue as its full URL, never a bare number: GitHub's structured closing references first, keyworded `Closes`/`Fixes`/`Resolves`/`Refs` references in the body only if those come back empty, and a reference that can't be resolved is a blocker; on Jira, the key. Classify it (standalone, epic child, or epic integration) per `workflow/pr-review.md` step 1: a feature-branch PR is an epic child only if the linked issue's parent is an epic — on GitHub, labeled `epic` (read by the parent's URL), with the issue and the parent both in the PR's repository; on Jira, of type Epic. Any other parent makes it standalone, noted in the report without asking — except, on GitHub, a parent outside the PR's repository (or of an issue outside it) or one that can't be identified: never match it to an `epic/<N>-` branch by number; mark the target branch **warn** and ask for manual validation. Write the PR intent — what it's for and what it deliberately leaves alone — and judge scope against it.
4. Check each Definition of Done item from `workflow/git-flow.md`, including the **Security checklist** and the PR's **Verification** section: mark **pass**, **fail** (blocker), or **warn** (unverifiable from the diff alone).
5. Recheck the snapshot first (`workflow/pr-review.md` step 5): if the PR closed, a repository, branch or SHA changed, or the recheck fails, stop and report both snapshots: no review of the current PR, and no automatic retry. Otherwise report the structured review: **Snapshot** (the reviewed SHAs and repositories, and whether coverage is complete), **Intent**, **Blockers**, **Suggestions**, and a **Summary**. Report blockers and unverifiable items, keeping coverage limits apart from code defects; never recommend or make the merge decision — that belongs to the human reviewer.

Never commit, push, modify files, approve, or merge. If any step fails, stop and report.
